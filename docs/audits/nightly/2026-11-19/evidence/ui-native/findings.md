# UI, native and offline audit — 2026-11-19

Baseline: `macdarenz-droid/M-arc` main **57dcbfc7efa60218ba902d16d6e3329d2fc053f5**. This is an audit, with no production changes. The source links below pin that exact commit. Original reports were leads, not evidence. Source inspection, isolated source probes, parent-reported browser observations and physical-device gaps are distinguished below.

## UI-N19-01 — P2 — Keyboard Options toggles the exercise instead of opening its menu

- **Location:** [Train.tsx:808](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/workout/Train.tsx#L808), nested [Options button:814](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/workout/Train.tsx#L814).
- **Trigger/reproduction:** Fresh PPL setup; start Push (skip check-in if offered); expand the first Machine Chest Press; focus that exercise's `Options` button and press Enter. The parent reviewer exercised this in the local browser built from the pinned source with external Windows case aliases for the build. Exercise `aria-expanded` changed from `true` to `false`, dialog count stayed zero. Pointer click on the same Options button opened the options successfully. Space is also consumed by the same source handler, but was not separately browser-exercised.
- **Expected/actual:** Keyboard activation should open the options sheet, just as pointer activation does. The containing `role="button"` keydown handler receives bubbled Enter/Space, prevents the native button activation and runs `onToggle()` instead. Stopping propagation only in the child's click handler is too late.
- **Impact:** Keyboard users cannot reliably access exercise options, including notes, swap/remove actions, through this control. [WCAG keyboard guidance](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) requires keyboard access to pointer-operable functionality.
- **Confidence/evidence:** High; exact source and actual browser reproduction supplied by the parent reviewer, with pointer control. This reviewer did not independently operate that browser.
- **Recommendation:** Make the collapse control a distinct native button adjacent to Options, or ignore keydown events whose target is not the header itself. Cover Enter, Space, header activation and pointer Options together.
- **Prior status:** Previous broad keyboard/UI findings are only partially resolved. Shared Card/Row keyboard support and reorder buttons are present, but this nested-control case remains. Do not describe every old accessibility issue as reopened.

## UI-N19-02 — P2 — Editing only conditioning distance preserves live provenance

- **Location:** [History.tsx:301](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/history/History.tsx#L301), [logging recomputation:310](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/history/History.tsx#L310), [distance input:341](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/history/History.tsx#L341).
- **Trigger/reproduction:** Edit a saved live conditioning/carry set from 20 m to 40 m without changing weight, reps, duration or effort; choose Save changes. `history-distance-edit` executes the exact `SessionEditor` function with synthetic hooks and captured JSX callbacks.
- **Expected/actual:** Edited set should receive `fidelity: 'edited'`. In the single-set fixture, liveShare should become 0 and timingTrusted false. Actual distance is 40 m but fidelity remains `live`, liveShare remains 1 and timingTrusted remains true.
- **Cause/impact:** The unchanged predicate compares weight, reps, effort and duration but omits `distanceM`. Subsequent logging recomputation trusts that incorrect fidelity. An edited performance entry continues to present itself to downstream models as live-quality evidence. The distance itself is saved correctly; this is a provenance defect, not loss of the entered distance.
- **Confidence/evidence:** High; deterministic exact-source callback probe in `probes.mjs` and `probe-results.json`. No browser assertion is claimed for this fixture.
- **Recommendation:** Compare every supported substantive set field, including distance, through a canonical comparison function. Verify distance-only edits, duration-only edits, unchanged save and a mix of edited/unedited sets.
- **Prior status:** Earlier History provenance fixes addressed the general edit path but leave this mode-specific omission open. Reassess prior UI-R04/A3-4 claims as partial, not wholly resolved.

## UI-N19-03 — P3 — Today calls a ready muscle fully recovered before the full threshold

- **Location:** [Today.tsx:32](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/today/Today.tsx#L32), [Today.tsx:131](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/today/Today.tsx#L131), [recovery thresholds](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/data/recovery.ts#L61).
- **Trigger/reproduction:** All trained muscles are ready, but at least one is between READY_PCT 90 and FULL_PCT 97. The exact Today renderer was run with one trained muscle at 95%, recovering false, ready true and fullInHours 3.
- **Expected/actual:** Text should report ready status or reserve full-recovery wording for the full threshold. It renders “Every muscle you have trained is fully recovered.” even though the same model has three hours remaining to full.
- **Impact:** Conflicting explanations across Today and the more precise Body detail misstate the app's own estimate. This finding proves an internal UI/model contradiction; it does not validate either threshold as a biological measurement.
- **Confidence/evidence:** High; exact-renderer probe and explicit current model constants. The brain review owns the scientific validity and uncertainty of the underlying recovery model.
- **Recommendation:** Use ready wording or test the full threshold for every relevant muscle, consistently with the Body detail. Include the 89/90/96/97 boundaries in a focused rendering check.
- **Prior status:** The Body `muscleFullText` distinction was corrected, but the Today surface still carries the old overstatement. Treat prior UI-07 as partial at the product level.

## UI-N19-04 — P2 risk — Same-ID native schedules can keep a stale payload after newer intent

- **Location:** [notifications.ts:62](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/native/notifications.ts#L62), [rest scheduling:111](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/native/notifications.ts#L111), [training scheduling:191](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/native/notifications.ts#L191).
- **Trigger/reproduction:** Mock the native bridge so an older `schedule()` is delayed, a newer schedule with the same notification IDs completes, then the older operation writes and completes. The actual notification module is bundled unmodified; only Capacitor notification operations are mocked. Rest: request 90 seconds, then 30 seconds. Training: request 20:00/Old split/silent, then 21:00/New split/alert.
- **Expected/actual:** Latest intent should be represented by the native pending payload. Actual rest fires at the older 90-second timestamp, 60 seconds later than intended. The latest run left 55 stale training payloads at 20:00 with Old split and `marc-training-silent` (number varies with current local time in the 56-day scheduling window).
- **Cause/impact:** Stale completion cleanup cancels only old IDs absent from `f.issued`. Reused IDs are deliberately retained, but there is no verification or reapplication of the latest payload. A stale operation writing the same ID can replace the current time, message and style. This can produce wrong rest timing and unwanted reminder timing/style.
- **Confidence/evidence:** High for the demonstrated JavaScript/native-boundary ordering weakness; **medium for physical-device occurrence**, because Android/iOS scheduling order was not exercised. Do not present the mocked bridge as evidence that the installed native plugin actually reorders these operations. Existing same-ID tests use equivalent payloads and assert pending counts, so they do not establish latest-content correctness.
- **Recommendation:** Serialize operations per notification family or reconcile pending payloads to a captured latest desired request after an in-flight operation settles. Test distinct timestamps, bodies and channels, not only IDs/counts; retain separate rest/training/backup ownership.
- **Prior status:** IMP-N01 cancellation races are partially addressed with sequence checks. The newer-on/older-on payload conflict remains a contract-level risk.

## UI-N19-05 — P2 conditional isolation risk — Worker cleanup and emergency reset assume sole ownership of the origin

- **Location:** [public/sw.js:22](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/public/sw.js#L22), [deletion:35](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/public/sw.js#L35).
- **Trigger/reproduction:** The hosting origin has a cache owned by a sibling application; activate this worker. The exact worker executed against synthetic CacheStorage with `other-app-v1` and `marc-old` deletes both. The loop also attempts to carry every cached `/assets/` URL, without checking M/ARC ownership.
- **Expected/actual:** Retain unrelated caches and carry only this application's prior build assets. Actual loop visits and deletes every cache other than the current cache. CacheStorage is the origin's named cache collection, not a private namespace for one worker: see [MDN CacheStorage](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage).
- **Impact:** A sibling app hosted on the same origin can lose its offline cache. No evidence establishes that the owner's actual browser has such a sibling cache today; this condition must remain visible in the finding.
- **Confidence/evidence:** High for the conditional source defect and deterministic activate-event probe; deployment/user exposure unverified.
- **Recommendation:** Prefix cache names with an app/scope identifier, filter old caches by that identifier, and restrict carried request URLs to the current app's base path. Include a sibling cache in a service-worker activation regression check.
- **Prior status:** New root cause in this audit. Existing 5xx navigation fallback fix is present; this is not a claim that REL-01 remains unresolved.

An additional, distinct cleanup mechanism has the same deployment assumption: [ErrorBoundary.tsx:23](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/app/ErrorBoundary.tsx#L23) calls `storage.clear()` and enumerates/deletes every IndexedDB database; the [startup reset:161](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/index.html#L161) does likewise. Triggering the explicitly confirmed emergency reset on a shared origin would erase sibling-app local-storage keys and databases as well. The UI describes deleting workouts on this device, not other hosted apps' data. This mechanism is source-traced only; **no destructive reset was executed and no real sibling-app data loss was observed**. The ordinary Settings reset uses narrower application-owned operations and is not the path alleged here. Recommendation: enumerate owned M/ARC keys/databases and preserve unrelated ones, or make isolated-origin deployment an explicit enforced constraint. The cache activation probe establishes the cache mechanism; it must not be cited as an executed database deletion test.

## UI-N19-06 — P2, prior issue open — Restore/reset does not reconcile the weekly backup reminder

- **Location:** [Settings.tsx:48](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/settings/Settings.tsx#L48), [weekly toggle:228](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/settings/Settings.tsx#L228), [boot reconciliation:71](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/main.tsx#L71).
- **Trigger:** With native weekly reminders scheduled, restore a backup whose `backupReminder` is false, or perform a replacement/undo that changes that preference. The reverse false-to-true restore is also affected.
- **Expected/actual:** Pending weekly notifications should follow the restored preference. `afterReplace()` cancels rest and resyncs training reminders but never calls `syncBackupReminder`. Boot and the individual toggle do call it; ordinary state replacement does not.
- **Impact:** UI preference and operating-system reminder can disagree until a later explicit toggle or cold start. This is source-traced, not an actual phone notification demonstration.
- **Confidence/evidence:** High static confidence in the missing reconciliation call; device behavior unverified. No new fixture was executed for this prior issue.
- **Recommendation:** Reconcile all notification families from the post-replacement state and test restore/reset/undo in both directions with a mocked pending-notification registry.
- **Prior status:** Open prior improvement-audit issue, not a new discovery to inflate the daily new-bug count.

## UI-N19-07 — P2 — History's session details have no keyboard expand control

- **Location:** [History.tsx:238](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/history/History.tsx#L238), [hidden notes/details:250](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/slices/history/History.tsx#L250), [Card's nested-control policy:22](https://github.com/macdarenz-droid/M-arc/blob/57dcbfc7efa60218ba902d16d6e3329d2fc053f5/src/ui/primitives.tsx#L22).
- **Trigger/reproduction:** Save a session with a note and open History. Parent browser inspection found the `.card-press` expansion element had no role or tabindex. Pointer clicking the card revealed the saved note and set. Each card always contains Edit, and may contain Share, so Card's interactive-descendant check disables its keyboard behavior. No separate expand button is rendered.
- **Expected/actual:** A focusable, labelled expand/collapse control should reveal the same notes and read-only session details. Actual available child buttons edit/share; they do not toggle the details. This is a different mechanism from Train Options' event bubbling.
- **Impact:** Keyboard users cannot reveal those History details through the card's only expand action. Editing a workout is a separate operation and does not replace a session-note/read-only-detail disclosure.
- **Confidence/evidence:** High source confidence, corroborated by actual browser DOM and pointer expansion. A full screen-reader session was not run; do not claim one was.
- **Recommendation:** Add an explicit native expand/collapse button with `aria-expanded` and `aria-controls`, keeping Edit/Share as siblings. Verify Tab, Enter/Space and pointer expansion without accidentally invoking Edit/Share.
- **Prior status:** Open remaining accessibility case despite the shared Card keyboard fix; it is not evidence that the entire shared fix failed.

## Verification and limits

`probes.mjs <checkout>` executes six named synthetic scenarios, including two notification payload cases. `probe-results.json` records their concrete results. It uses the checkout's TypeScript and esbuild, generates scratch bundles alongside itself and never calls a real provider, notifications service or health plugin. Generated `.bundle.mjs` files are build scratch, not intended for publication. Root owns the full repository test/check results and browser artifacts.

Parent browser evidence covers the Options keyboard/pointer comparison and five theme switches: pressed state and expected body colors changed, with no horizontal overflow at 1280 px. It also exercised saving one 20 kg × 8 ideal set, History pointer expansion and a persisted edit to 20 kg × 9; Body at 375 px (body width 360 px); rejected waist 40/neck 90 input; and a normal 180 cm height/40 cm neck/90 cm waist example displaying 18.4%. Escobar consent opened without enabling it, and parent reported zero browser error logs. A rest banner briefly visible after Finish was investigated: `finishSession` clears active state and cancels the notification; `RestBanner` retains the previous frame for `durFor('exit') + 40 ms`. It had disappeared by History navigation, so **no rest lifecycle defect is claimed**.

Those checks do **not** prove contrast/accessibility across every component, mobile viewport or future theme. No physical Android/iOS device, watch, OS permission dialog, screen reader, offline install/update lifecycle, native share target, camera picker or delivered notification was exercised by this reviewer. No claimed research validation of exercise instructions or recovery estimates is implied by the UI trace.
