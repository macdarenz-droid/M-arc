## Why: six full renders of the same tree per run

**What `generate --check` costs.**
- It is `render()`, which runs every plugin (generate.mjs:40-63; 501 outputs today), then `diff()`, which reads each file (:71-80).
- In the scratch probe, one render took 418 s of wall time on that box:

  | plugin | outputs | s |
  |---|---|---|
  | `gen/plates.mjs` | 96 | **391.4** |
  | `gen/zooms.mjs` | 94 | 10.0 |
  | `gen/feel.mjs` | 95 | 5.6 |
  | `gen/ids.mjs` | 5 | 5.4 |
  | `content.mjs`, `library-gate.mjs`, `hands.mjs`, `handpairs.mjs`, `variant-gate.mjs` | 319 | 3.3 together |
  | headers and hashes | 501 | 1.2 |

- `diff()` took 0.1 s. The whole map is 12.9 MB of JSON, which decodes in under 0.1 s.
- **`plates.mjs` is 94 % of every render.**
- On a CI runner, a render alone takes 192 s. The gate-shard job logged `generate --check: PASS, 501 files fresh (191981 ms)`.

**How many renders a run makes.** A vitest run on main renders the repo's own tree six times:
1. **Once in the walk cache.** `renderOf(ROOT)` (walk-cache.ts:112-114) uses `memo` (:65-87): one process computes a tree key, the others wait on its lock (:73-78), and every caller gets a fresh decode (:71, :84).
   - Its callers are lb1:1053, lb2:875, lb3:265, lb5:277, lb6:355, library-core:20, library-rows:44 and library-shared:186.
   - lb5's 0.3-0.5 s in all four jobs is a cache hit.
2. **Five more times, one per lane.** Each runs `gen.render()` in its own awaited child, and none uses the cache:
   - lb4:236-241, lb7:320-325, lb8:328-333, lb9:1138-1143, lb10:1162-1167;
   - F-VITEST-RPC-2 left them as "load, not blocks" (see its card's Not in scope).
- `inputsMapOf(ROOT)` (walk-cache.ts:116-120, called at library-ci:342) runs every plugin's outputs once more. That is by design: affected.mjs:71-76 builds the map "without editing the generator" and proves it against render's headers.

**When they run.**
- On source-gate, lb10, lb9 and lb8 each started a full render within about 22 s of the run's start (21:25:13). Their children logged 652.9-665.0 s and ended at 21:36:31-35.
- So three renders started together on one 4-vCPU runner, against 192 s for one render alone.
- vitest seems to start the largest files first. That is inferred from the log order and not verified.

**Growth.**
- W9 added 50 generated files (451 → 501, from `2a898c3e` to `505ea13a`). W10 (#434) adds 22 more.
- `plates.mjs` costs about 4 s per plate row on the probe box, and every wave adds rows. So each wave moves all six copies toward the limit.

**Scratch-tree renders are a second class.** Each renders a changed copy of the repo, so it has a different key and cannot share the repo's render.
- The largest seen:
  - lib7b 7b-A2 renders a full copy plus 3 scratch rows (tests/library/fixtures/lib7b/fixture.mjs:24, :49-51). It took 376 s to past 600 s.
  - zoom-none A1 took 144-199 s.
  - library-ci C4 took 472-708 s, under its own 1,200,000 ms limit (library-ci:318).
- They all run on the same loaded CPU.
- The lib2b own-rows trees are small: E1's render on such a tree is 27-36 s.

## Options weighed

- **A. Share the render (recommended).** The five lane tests read the run's one walk-cache render instead of rendering again.
  - This removes 5 of the 6 repo renders per job (about 5 × 192 s of CPU per job [est]), and the three-renders-at-once start.
  - Every check stays:
    - the same regexes, `diff` and `expect` lines;
    - the render is the same function on the same tree;
    - the key covers every byte of the tree (walk-cache.ts:28-46), and the file is re-keyed when it is read (below).
  - It is the form lb3 and lb6 already use (F-GEN-WALK-SPEED), plus one helper.
- **B. globalSetup renders the repo before any test, awaited: not now.**
  - It is the strongest decoupling, because no test's limit includes the render.
  - But every vitest run would pay it at the start:
    - the `MARC_PERF` second run inside `npm test` (package.json:11);
    - every focused local run of an unrelated file: 3-7 min on the probe box.
  - Whether vitest 3.2.7's globalSetup can see which files a run selected is not verified.
  - B is the fallback under Stop 1.
- **C. Make the render faster: a follow-up card, F-GEN-SPEED, not this one.**
  - It is the only lever for the scratch-tree class (7b-A2) and for growth, and the probe points it at `plates.mjs`.
  - It edits `tools/plates/gen/**` or `tools/plates/library/**`. A writer plugin is part of every output's `inputsSha256`, so it moves headers the way F-GEN-HELD-CLEAN does. So it is its own PR, in a slot between waves.
- **D. Raise the 600 s limits: rejected.** It is not a fix: it hides growth, and the next wave crosses the new number. Q-GCS-4 names the proof any raise would need.
- **E. Check less: never.**
  - An incremental `--check` that trusts each header's `inputsSha256` instead of rendering is also rejected. It would pass a stale output whenever an inputs list is incomplete, which is what `--check` exists to catch.
- **Not folded:** `inputsMapOf(ROOT)` into the shared render. Its worth is that it is built apart from `render()` and checked against render's headers; sharing would make that proof circular.

## The change (A, as recommended in Q-GCS-1)

1. **`tests/walk-cache.ts`, add-only:**
   ```ts
   /** F-GENCHECK-SHARE: the file holding this run's one render() of the tree at `root` (renderOf's stored text: JSON of
    *  the map's entries), so an awaited child can check it without rendering again. Throws outside a vitest run, and when
    *  nothing is stored for the tree as it is now (it changed while or after it rendered): never a render of another tree. */
   export async function renderFileOf(root: string): Promise<string> {
     await renderOf(root);
     const dir = cacheDir(), file = dir ? join(dir, `render-${treeKey(root)}.json`) : '';
     if (!file || !existsSync(file)) throw new Error(`walk-cache: no stored render of ${resolve(root)} (outside a vitest run, or the tree changed while it rendered)`);
     return file;
   }
   ```
   - In `memo`, one stderr line when a compute ends (Q-GCS-6):
     - `[walk-cache] <name> <key, 12 hex> computed in <s> s`, after the store at :83;
     - `[walk-cache] <name> <key, 12 hex> not stored: the tree changed while it computed`, when it did not store.
   - Nothing else in the file changes: not the key, the lock, `renderOf`, `inputsMapOf` or `feelAllOf`.
2. **The five lane tests.** In each A9 body, only the line that makes `out` changes, plus one line that gets the file.
   - For lb4, lb7 and lb8, the two comment lines above `const script` become one comment and the `file` line, so the line count is unchanged.
   - lb9 and lb10 have no comment there, so they gain the one `file` line.
   - Exact form (lb8:326-329; lb4:234-237 and lb7:318-321 the same):
     ```
     -    // In a child process, awaited (VITEST-RPC ruling A, #276): an in-process render blocks the worker past vitest's 60 s
     -    // RPC limit on a loaded runner. The child prints the diff and, per output, whether it names an LB8 path.
     +    // F-GENCHECK-SHARE: the awaited child reads the run's one render of the repo (tests/walk-cache.ts) and checks it.
     +    const file = await (await import('../walk-cache')).renderFileOf(new URL('../../', import.meta.url).pathname);
          const script = `const gen = await import(${JSON.stringify(new URL('../../tools/plates/generate.mjs', import.meta.url).href)});
     -const ids = ${JSON.stringify(LB8)}, out = await gen.render(), bad = [];
     +const ids = ${JSON.stringify(LB8)}, out = new Map(JSON.parse((await import('node:fs')).readFileSync(${JSON.stringify(file)}, 'utf8'))), bad = [];
     ```
   - lb9:1137-1139 and lb10:1161-1163 insert the `file` line right after the `it(` line. Their comment is optional.
   - **Byte-identical in all five:**
     - the test name;
     - the `for` lines and their regexes;
     - the `console.log(JSON.stringify({ diff: gen.diff(out), bad, n: out.size }))` line;
     - the `execFile` call;
     - the three `expect` lines and the `{ timeout: T }`.
   - The timing `console.log` may say `check took` instead of `render took`. It is a log, not an assertion.
   - The `(await import('../walk-cache'))` form keeps lb7 from gaining an import line. tsconfig has no `noUnusedLocals` (tsconfig.json:9-21), so lb7's `execFile` and `promisify` imports stay as they are.
3. **A new `tests/howto/f-gencheck-share.test.ts`** pins the change (Acceptance G2, G3) and runs its own mutations (m1-m4).

Why this form keeps every check:
- The child still runs `gen.diff(out)` on the disk as it is at the test's time.
- `out` is the same `Map(path → { text, writers, hash })` that `render()` returns. walk-cache.ts:114 stores `JSON.stringify([...render()])` from a node child of the same tree.
- The key is checked again when the file is fetched.
- The checks still run in an awaited child, so no new worker block is added (F-VITEST-RPC-2's 30 s guard and 15 s budget still apply).
